Each section names a moment, the command for it, and what to do with the result. Commands print JSON when piped, so the examples use `jq`.

## The agent loop

### 1. Before trusting a document

```sh
hibi check --doc CLAUDE.md
```

Run this before acting on an instruction file, a README, or any page in a knowledge repository.

| exit | meaning | what to do |
|---|---|---|
| `0` | no claim on the document gates | use the document; read any warnings in `reasons[]` |
| `2` | at least one claim gates | do not act on the flagged sentences as written; read their `verdicts[]` entries |
| `1` | operational error, including a document with no registered claims | read `error` |

Under `--doc`, an `expired` claim gates. In a whole-store `check` it only warns. If no claim is registered for the document, `check --doc` exits 1 with `no claims are registered for <path>; run hibi audit --doc <path>`: hibi knows nothing about the file, which is different from the file being clean. Run `audit` on it (section 3).

The contradiction pass under `--doc` judges only the pairs with a claim in that document, so the check stays fast in a large store. A pair's other claim may be on any document.

### 2. After a change

```sh
hibi check --since origin/main
```

Only claims whose doc or evidence side names a file changed since the ref are evaluated. The JSON adds `since` and `changedFiles`. `documents[].suspect[]` lists each claim that gates or warns, with its most severe status. Fix the prose in the same change, then follow each verdict's `remediation` (usually `hibi reanchor <id>` after you re-read the sentence). An unknown ref exits 1.

Under `--since` the contradiction pass still runs over the whole store, so a scoped check still reports a conflict with a claim outside its scope.

### 3. A new or unaudited document

```sh
hibi audit --doc docs/pricing.md
```

`audit` returns one row per region (sentence, heading, list item, table row, fenced block). A covered row names its claim. An uncovered row has a kind from the judge's triage: `code`, `reference`, `attested`, `unverifiable`, `not-a-claim`, `unsure`, or `pending`. See [Audit](/audit).

For each uncovered `code`, `reference`, or `attested` row, decide the evidence and record the claim. Recording is never automatic. Send a batch:

```sh
echo '[
  {"doc":"README.md","docQuote":"Retries are capped at 5 attempts.","kind":"code",
   "code":[{"file":"src/retry.ts","quote":"MAX_ATTEMPTS = 5"}]},
  {"doc":"docs/pricing.md","docQuote":"The Pro plan costs $29 per month.","kind":"attested",
   "ttl":"P90D","owner":"human:alice@example.com","by":"agent:opus",
   "sources":[{"id":"stripe","resource":"https://dashboard.stripe.com/products/prod_123"}],
   "procedure":{"instructions":"Open the Stripe dashboard and report the Pro monthly price.",
                "steps":[{"id":"price","command":"stripe prices list --product prod_123"}]}}
]' | hibi record --from-file - --by agent:opus
```

`record` adds one `vouch` attestation by the item's `by`, or by `--by` when the item has none. `by` is required one way or the other; there is no default. An `attested` claim recorded with `"by": "agent:…"` has no counting attestation, so it is expired from the start: it warns in `check`, gates in `check --doc`, and appears in the worklist with reason `expired` until evidence is judged `supports` or a human vouches.

For an `unverifiable` row, rewrite the sentence as an attributed opinion, or remove it. Run `audit` again to confirm.

### 4. Periodic hygiene in a knowledge repository

Run a whole-store check and read the worklist:

```sh
hibi check | jq '.worklist[] | {claimId, reason, sentence, procedure, sources, owner}'
```

Each worklist item has a `reason`:

| reason | meaning | what to do |
|---|---|---|
| `expired` | a claim's ttl ran out (any kind with a `ttl`) | for an `attested` claim, follow `procedure` and `sources`, then submit evidence; for a `code` or `reference` claim, re-read it and ask a human to vouch |
| `never-checked` | an `attested` claim with a `procedure` or `sources` has never had evidence judged | follow `procedure` and `sources`, then submit evidence |
| `review` | the judge was not sure, or the evidence did not address the sentence | submit evidence that addresses the sentence directly (`attested` claims), or acknowledge |
| `pending` | the judge could not answer (no key, network down, or an answer it could not use), or a referenced span is over 32,000 characters | set `TYPESAFE_API_KEY` and run `check` again; for `judge error: …`, read the message |

An `attested` claim with no `procedure` and no `sources` (a pure vouch) is never listed as `never-checked`.

`hibi list --state pending` returns the same claims as one row each. `lastEvidence` on an item shows the summary, source, time, and actor of the newest judged evidence.

Collect the evidence the procedure asks for, then submit it:

```sh
echo '[{"claimId":"clm_1a2b3c4d5e6f7a8b",
        "evidence":"Pro plan: $29.00 per month, billed monthly.",
        "source":"stripe",
        "summary":"Stripe lists Pro at $29/month"}]' \
  | hibi evidence --from-file - --by agent:opus
```

Evidence applies to `attested` claims only; an item naming a `code` or `reference` claim rejects the batch. A `supported` result appends an `evidence` attestation, which resets the ttl. A `refuted` result gates the claim: fix the sentence or the source of truth. See [Attestations](/attestations).

Then look at contradictions and duplicates:

```sh
hibi list --state conflict    # claims with a contradiction finding, gating or review
hibi list --state duplicate   # duplicate candidates and claims with the same sentence
```

Reconcile a contradiction by rewriting whichever sentence is wrong. If both are correct (for example, they describe different plans), acknowledge it. See [Conflicts](/conflicts).

### 5. Scheduled evidence collection

Hibi never runs `procedure.steps` and never fetches a `sources[].resource`. An outer runner does: a Lobster workflow, a cron job, or a scheduled CI job. The runner reads the worklist, runs the steps it trusts, and pipes the results to `hibi evidence`.

A minimal cron script that handles items whose procedure has steps:

```sh
#!/bin/sh
# Runs the commands stored in .claims/; review them before scheduling this.
hibi check | jq -c '.worklist[] | select(.procedure.steps != null)' |
while read -r item; do
  id=$(echo "$item" | jq -r .claimId)
  out=$(echo "$item" | jq -r '.procedure.steps[].command' | sh 2>&1 | head -c 32000)
  jq -n --arg id "$id" --arg ev "$out" \
    '[{claimId: $id, evidence: $ev, source: "procedure steps", summary: "output of the stored steps"}]' |
    hibi evidence --from-file - --by process:cron
done
```

`steps` uses the Lobster step shape (`id`, `command`, optional `stdin`), so a Lobster workflow can run the same steps. Evidence is limited to 32,000 characters per item. Items without steps need an agent that reads `procedure.instructions`.

A `process:` actor can submit evidence, and judged evidence counts toward the ttl. A `process:` or `agent:` vouch does not.

## The human loop

The owner of an `attested` claim is the actor to contact when it expires.

```sh
hibi list --state expired | jq '.claims[] | {claimId, sentence, owner, ttl, expiresAt}'
```

`expiresAt` is null when the claim has a ttl and no counting attestation; such a claim is already expired.

The owner re-checks the fact and vouches:

```sh
hibi attest clm_1a2b3c4d5e6f7a8b --by human:alice@example.com --note 'checked Stripe, still $29'
```

Only a `human:` vouch or judged evidence resets the ttl. The result's `countsTowardTtl` says whether the attestation resets it.

To accept a finding instead of changing a sentence, acknowledge it with a note:

```sh
hibi attest <id> --by human:alice@example.com --ack review --note "the dashboard wording differs; the price matches"
hibi attest <id> --by human:alice@example.com --ack conflict:<other-id> --note "the FAQ describes the annual plan"
```

An ack stops that finding from warning or gating. It never resets the ttl. A conflict ack is recorded on both claims and lapses when either sentence changes.

## CI

Run `hibi check` on every pull request and `hibi check --since <base>` to scope it. See [CI](/ci) for the GitHub Action, the API key as a secret, and what runs without a key.
