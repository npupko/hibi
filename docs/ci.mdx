`hibi check` has one exit-code contract, so it works anywhere a non-zero exit blocks: a CI job, a git hook, or an agent's session hook.

| exit | meaning |
|---|---|
| `0` | clean, or warnings only |
| `2` | gating: a `changed`, `orphaned`, or `ambiguous` side, a `refuted` judgment, or a contradiction at or above the threshold on an enforced claim; `expired` under `check --doc`; any warning under `--fail-on warn` |
| `1` | operational error: no store, an unknown flag, an unknown `--since` ref |

## GitHub Action

The repository is a composite action. It installs Bun, then runs `hibi check` with the binary on `PATH`, or `bunx @npupko/hibi` when there is none.

```yaml
name: hibi
on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    env:
      TYPESAFE_API_KEY: ${{ secrets.TYPESAFE_API_KEY }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0   # needed when `since` compares refs
      - uses: npupko/hibi@v0
        with:
          fail-on: gating
          since: origin/${{ github.base_ref }}
```

### Inputs

| input | default | effect |
|---|---|---|
| `fail-on` | `gating` | passed as `check --fail-on`: `gating`, `warn`, or `never` |
| `since` | empty | when set, runs `check --since <ref>`: only claims touching files changed since the ref |
| `doc` | empty | when set, runs `check --doc <path>`: only claims on that document, and `expired` gates |
| `working-directory` | `.` | the directory that holds `.claims/` |

### The API key

The judge reads `TYPESAFE_API_KEY` from the environment. Store it as a repository secret and set it in the job's `env`, as above. The action passes no key of its own.

### What runs without a key

Most of `check` needs no key:

- anchor resolution of every doc and evidence span;
- expiry from attestations and ttl;
- every judge verdict already in `.claims/judge/` (the cache is read, never re-asked);
- the comparison of numbers, money, versions, and dates, which happens in code.

A judgment that is not in the cache comes back `pending`. `pending` is a warning, so it does not fail the build under the default `fail-on: gating`. Under `fail-on: warn` it does.

Commit `.claims/judge/` with the rest of the store. When the cache already holds every verdict the tree needs, CI asks the judge nothing and gives the same verdicts with or without a key. See [Judge](/judge).

### Strictness

| `fail-on` | the build fails when |
|---|---|
| `gating` | any enforced claim gates. The default. |
| `warn` | any enforced claim gates or warns (`moved`, `review`, `pending`, `unavailable`, an `expired` claim in a whole-store check, a conflict below the threshold) |
| `never` | never. The JSON still reports everything. |

`suggested` and `retired` claims never gate or warn under any setting.

## Audit as a gate

```sh
hibi audit --doc plan.md --fail-uncovered
```

Exits 2 while any uncovered region of the document is triaged as `code`, `reference`, or `attested` at or above the threshold, and 0 once each such region is covered by a claim. Without a key, uncovered regions are `pending` and do not fail this gate. See [Audit](/audit).

## git hooks

```bash pre-push
#!/bin/sh
hibi check --since origin/main || {
  echo "hibi: a document sentence is stale; re-verify before pushing." >&2
  exit 1
}
```

```bash pre-commit
#!/bin/sh
hibi check || {
  echo "hibi: a document sentence is stale; re-verify before committing." >&2
  exit 1
}
```

`check --since <ref>` suits a pre-push hook. Plain `check` suits a pre-commit hook. The same commands work in lefthook or husky. `check` writes nothing except new judge cache entries.

## Output in CI

Output is JSON when stdout is not a terminal. Useful flags:

| flag | effect |
|---|---|
| `--no-hints` (or `HIBI_ADVICE=0`) | drops the `remediation` menu for shorter logs |
| `--explain` | adds `detail` to each verdict: located regions, span changes, similarity |
| `--format human` | the terminal report, if you prefer it in logs |
