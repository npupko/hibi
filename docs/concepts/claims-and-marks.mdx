hibi keeps three kinds of records. None of them is ever edited or deleted.

## Claim

A claim is a statement that was checked, and what it was checked against.

| Field | Meaning |
|---|---|
| `statement` | The statement, as text. Stored trimmed. |
| `subject` | One [anchor](/concepts/anchors): the unit the statement is about, usually the sentence in a document that makes it. |
| `evidence` | Zero or more anchors: the units that support the statement, usually declarations in code. Order matters; evidence is numbered from 1. The same evidence anchor twice is `invalid_argument`; the subject may also be evidence. |
| `recheck` | Optional. An ISO 8601 duration such as `P90D` or `P6M`. After this long the claim is expired even if nothing changed. |
| `note` | Optional. How to check the claim again, or where the truth lives. |

A claim with no evidence is allowed. Its subject alone is fingerprinted, so it
goes stale when the sentence changes. With a `recheck` period it also expires
after that time, which suits statements whose truth lives outside the
repository:

```bash
hibi claim "Each attempt times out after 10 seconds." \
  --subject "file:docs/retry.md::times out after 10 seconds" \
  --recheck P90D \
  --note "The timeout is set by the HTTP client defaults; check its release notes."
```

The "sides" of a claim are its subject (side 0) and its evidence (side 1, 2
and so on).

## Mark

A mark records that the claim was checked: the time (`at`), optionally who
(`by`) and a `note`, and the fingerprint of every side as it was at that
moment. `hibi claim` writes the first mark itself. `hibi mark` adds another
after a re-check. A claim can have any number of marks.

```bash
hibi mark c1-xwck --note "200 << n equals 200 * 2^n" --by agent:claude
```

```text output
c1-xwck2bdefbx39g56m7dn  marked  m1-t1r68ygfdz8m7zfjymxm
  was stale: evidence 1 file:src/retry.rs changed (fingerprint_differs); now marked: make sure you re-checked it
    evidence 1 is now:
    | pub fn delay_ms(n: u32) -> u64 {
    |     200 << n
    | }
```

`mark` requires every side to resolve to exactly one unit, exactly. A side
that is missing or matches several units makes the command fail with
`side_missing` or `side_ambiguous`; use `reanchor` to point that side at the
right unit. That includes a side whose stored anchor is no longer found
exactly: `mark` never follows a candidate.

`mark` prints which sides were not the same, not what changed in them. Read
the change, for example with `git diff`, before you mark.

## Retirement

A retirement records that a claim no longer applies. It is permanent. A
retired claim stays in the store, is no longer evaluated, and no longer covers
anything.

```bash
hibi retire c1-2kfx --note "The docs no longer state the attempt limit."
```

```text output
c1-2kfx78rwbb7wyxwst92f  retired  r1-yxm06xchd4ax4ggtgh2n
```

`--replaced-by <claim-id>` names the claim that takes the place of the
retired one. It must be a live claim, not one of those being retired.

## Changing a claim

Claims are immutable. `hibi reanchor` builds a new claim from an old one and,
in one write, stores the new claim, a mark for it and a retirement of the old
claim that names the new one in `replacedBy`. Use it to change the statement,
replace or add or drop an anchor, or change the `recheck` period or the note:

```bash
hibi reanchor c1-c5dm \
  --statement "The client gives up after 3 attempts." \
  --subject "file:docs/retry.md::gives up after 3 attempts"
```

If the rebuilt claim is the same as another live claim, by the rule of
[running the same claim again](#running-the-same-claim-again), `reanchor`
marks that claim and retires the old one into it instead of writing a new
claim; the JSON result then has `"merged": true` and `new` is the id of the
existing claim. Like `mark`, the result reports what
the old claim was before the write.

Without options, `reanchor` resolves every side again and stores each
selector as it is completed now, with the current text around each quote and
its current container. Every side must resolve exactly, as
for `mark`. When nothing changed since the selectors were stored, it writes
nothing. For a claim in another example repository whose files did not
change:

```text output
$ hibi reanchor c1-rp2q
error: no_change: re-anchoring c1-rp2qmeyffhx5f4vs0sc3 would produce the same claim
  fix: The stored anchors are up to date. To record a new check, run hibi mark c1-rp2qmeyffhx5f4vs0sc3
```

Evidence numbers in `--evidence` and `--drop-evidence` are the numbers of
the old claim. A kept side that does not resolve exactly is named by its old
number too, also when a lower number is dropped in the same command. Here
the declaration of evidence 2 was renamed from `RETRIES` to `MAX_RETRIES`:

```text output
$ hibi reanchor c1-70dn --drop-evidence 1
error: side_missing: evidence 2 (file:src/limits.py) resolves to no unit (selector_not_found): the selector matches no unit
  fix: hibi reanchor c1-70dnhqhzcddqnj6ry2dy --evidence 2=<anchor>
```

Because `reanchor` writes a mark, run it only after you checked the statement.

## Ids

Every record has an id derived from its content: `c1-` for a claim, `m1-` for
a mark, `r1-` for a retirement, followed by 20 characters of a BLAKE3 hash of
the record. Two consequences:

- A claim with exactly the same statement, stored anchors, `recheck` and `note`
  is the same claim.
- A claim with the same body as a retired claim is that retired claim, and
  `claim` fails with `claim_retired`. To record the same statement and anchors
  again, give a different `--note`.

## Running the same claim again

Running the same `hibi claim` again adds a mark to the existing claim and
prints `marked` instead of `created`. The stored anchors hold the text around
a quote and its container (see [anchors](/concepts/anchors)), and you may
write an anchor differently the second time, so the new claim could get a
different id. hibi therefore looks for a live claim that is the same in
every other respect: the same statement, `recheck` and `note`, the same
number of sides with the same locators, and every stored side resolving to
the same unit as the anchor you gave. Selectors are not compared, so
`#MAX_ATTEMPTS` and a quote on that constant name the same side, and so do a
quote and a longer quote in one sentence. If it finds such a claim, it marks
it (the one with the smallest id if there are several) and does not rewrite
its stored anchors. The result says what the claim was before the mark. This
is how a stale claim shows up when you claim it again after the function
changed:

```text output
$ hibi claim "Old entries are evicted first." --subject "file:docs/cache.md::evicted first" --evidence "file:src/cache.rs#evict"
c1-msg51e29yny7wkpesxnw  marked  m1-j3f4k474zx9f4jjme97j  subject file:docs/cache.md (sentence "Old entries are evicted first.", line 4); evidence 1 file:src/cache.rs (function "evict", line 8)
  was stale: evidence 1 file:src/cache.rs changed (fingerprint_differs); now marked: make sure you re-checked it
    evidence 1 is now:
    | pub fn evict() { drop_oldest(); }
```

In JSON each entry carries `accepted`: `null` for a new claim, otherwise
`{"was": <state before>, "sides": [...]}` listing the sides that were not
`same`, each with `index`, `role`, `loc`, `state` and `reason`. The lines
after "is now:" show the text that was accepted.

Here the claim was made with the quote `gives up after 3 attempts`, and is
claimed again with the whole sentence:

```text output
$ hibi claim "The client gives up after 3 attempts." --subject "file:docs/retry.md::It gives up after 3 attempts." --evidence "file:src/retry.rs#MAX_ATTEMPTS"
c1-2kfx78rwbb7wyxwst92f  marked  m1-6hscmehqkbswsx2a3wbw  subject file:docs/retry.md (sentence "It gives up after 3 attempts.", line 4); evidence 1 file:src/retry.rs (variable "MAX_ATTEMPTS", line 2)
```

In JSON the entry has `"created": false`. A side of the existing claim must
resolve to exactly one unit. When it is `missing` or `ambiguous`, for
example after its heading was renamed, the existing claim is not the same
claim, and `claim` writes a second one. Re-anchor the existing claim
instead. Only live claims are matched: after a claim is retired, the same
command creates a new claim, or fails with `claim_retired` when it builds
exactly the retired claim.

Commands accept a unique prefix of an id with at least 4 characters after the
type prefix, such as `c1-c5dm`. A prefix that matches several records is the
error `ambiguous_id`, and the message lists them.

## Reading the history

`hibi list` reads the store only: nothing is resolved and no state is
computed, so it works when files or providers are missing.

```bash
hibi list --retired
```

```text output
c1-2axv59jx0ztvfjd1adn9  The delay doubles each time, starting at 200 ms.  file:docs/retry.md  1 mark  last 2026-11-21T08:59:35Z
c1-2kfx78rwbb7wyxwst92f  The client gives up after 3 attempts.  file:docs/retry.md  2 marks  last 2026-11-21T08:59:35Z  retired
c1-c5dm2jvhr8hb36rx5rgm  The client gives up after 5 attempts.  file:docs/retry.md  1 mark  last 2026-11-21T08:59:34Z  retired
c1-xqhbms40kkesq10rxjen  Each attempt times out after 10 seconds.  file:docs/retry.md  1 mark  last 2026-08-01T09:00:00Z
c1-xwck2bdefbx39g56m7dn  The delay doubles each time, starting at 200 ms.  file:docs/retry.md  2 marks  last 2026-11-21T08:59:35Z  retired
```

With an id, `list` prints the stored claim, its marks in time order and its
retirement:

```bash
hibi list c1-c5dm
```

```text output
c1-c5dm2jvhr8hb36rx5rgm
  statement: The client gives up after 5 attempts.
  subject: {"loc":"file:docs/retry.md","sel":{"quote":"gives up after 5 attempts","prefix":"It","suffix":".","within":["Retries","The client retries a failed download."]}}
  evidence 1: {"loc":"file:src/retry.rs","sel":{"symbol":"MAX_ATTEMPTS"}}
1 mark:
  m1-pdfqery1ae16y8n6r17r  2026-11-21T08:59:34Z
    file:docs/retry.md  b3:prose-v1:0233c89ebf2069292e2778bdc7176396
    file:src/retry.rs  b3:ast-v1:fb3a4a42c90a9093fe98969b8a0018c0
retired: r1-kzkbw96d81jyq607m4sy  2026-11-21T08:59:34Z  replaced by c1-2kfx78rwbb7wyxwst92f
```

`--loc <glob>` keeps claims with a side whose locator matches, and
`--text <substring>` keeps claims whose statement contains the text
(case-sensitive).
