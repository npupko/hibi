## Claim states

hibi evaluates a claim from the claim, its marks, its retirements, the current
resolution of each side, and the current time. Nothing else. The first row
that applies decides:

| Order | Condition | State |
|---|---|---|
| 1 | The claim has a retirement | `retired` |
| 2 | No mark matches: no mark has, for every side, a fingerprint equal to the side's current one | `stale` |
| 3 | The claim has no `recheck` period | `fresh` |
| 4 | Some matching mark is younger than the `recheck` period | `fresh` |
| 5 | Otherwise | `expired` |

Consequences:

- **Any matching mark counts, not only the newest.** Reverting a file to
  content that an older mark covers makes the claim fresh again.
- **A claim with no mark is stale.** `claim` writes the first mark itself, so
  this happens only if a write was interrupted.
- **Expired means unchanged but old.** The content still equals a marked
  state; only the time ran out. At exactly the end of the period the claim is
  already expired.
- **A stale claim still covers its units** for [coverage](/coverage).

## Side states

`status` reports each side that is not `same`, with a state and a reason:

| State | Reason | Meaning |
|---|---|---|
| `same` | | The unit's fingerprint equals the one in the reference mark |
| `changed` | `fingerprint_differs` | The unit was found and its fingerprint differs |
| `changed` | `no_mark` | The claim has no mark |
| `missing` | `selector_not_found` | The resource exists, but no unit matches the anchor |
| `missing` | `not_exact` | No unit matches the anchor exactly; `candidates` lists the units found by similarity |
| `missing` | `resource_not_found` | The file or resource does not exist |
| `ambiguous` | `several_units` | The anchor matches several units; `candidates` lists them |
| `unavailable` | `profile_mismatch` | The fingerprints use different profiles, for example a whole code file that no longer parses |
| `unavailable` | `resource_unavailable` | The resource exists but cannot be read now: a code file that does not parse, for an anchor with a symbol, or git's file list cannot be read |
| `unavailable` | `scheme_not_declared` | The locator's scheme is not declared in `.hibi/hibi.toml`, for example after its declaration was removed |
| `unavailable` | `provider_not_registered` | The scheme is declared, but your user config has no command for it. No command is run. |
| `unavailable` | `provider_failed` | The provider command could not start, timed out, broke the protocol or was killed |
| `unavailable` | `provider_error` | The provider answered with an error, or returned a unit hibi rejects |
| `unavailable` | `not_text`, `too_large` | The file is not valid UTF-8, or is too large: a code file over 2 MiB, another file over 8 MiB, or more than 100,000 units |
| `unavailable` | `repo_not_found`, `repo_not_allowed` | A sibling repository could not be used (see [configuration](/configuration#sibling-repositories)) |

A side is never resolved by similarity. A candidate is a guess at where the
unit went, for you to read; the side stays `missing` until you re-anchor it
(see [anchors](/concepts/anchors#finding-the-unit)).

An unavailable side also carries `detail`, the message that says why, from
the provider or from hibi, and `remediation`, what the limit or the cause is
and what you can do. The text
output prints both under the side. For a scheme whose declaration was
removed:

```text output
$ HIBI_CONFIG=user.toml hibi status
1 claim: 0 fresh, 1 stale, 0 expired, 0 retired

c1-regrhf1hta0k48q82xea  stale  Downloads are retried at most 3 times.
  marked 2026-11-21T03:02:34Z (m1-mha0ka4z0safgnbcw30b)
  subject  ref:notes  unavailable (scheme_not_declared)
    the scheme ref is not declared in .hibi/hibi.toml
    Declare the scheme under [schemes] in .hibi/hibi.toml, or retire the claim.
```

The reference mark, against which side states are reported, is the newest
matching mark if any mark matches, otherwise the newest mark. Marks with the
same time, to the second, are ordered by id, so of two marks made within one
second either can count as the newest. The text output
of `status` names it, with its time, under each listed claim, together with
the recheck period and when it runs out. For a side that is missing or
ambiguous it also prints the stored symbol, quote or key, so you can see what
the anchor was looking for.

## Recheck periods

`--recheck` takes an ISO 8601 duration with whole numbers: `P90D`, `P6M`,
`P1Y`, `P2W`, `PT12H`. Years and months move the calendar date, using the
last day of a shorter month; weeks, days, hours, minutes and seconds add fixed
seconds. A period of zero is refused:

```text output
$ hibi claim "x" --subject "file:docs/cache.md::holds 64 entries" --recheck P0D
error: invalid_duration: the recheck period "P0D" is zero; it must be longer than zero
  fix: Give a period longer than zero, for example P90D, or leave the recheck period out.
```

```bash
hibi claim "Each attempt times out after 10 seconds." \
  --subject "file:docs/retry.md::times out after 10 seconds" \
  --recheck P90D \
  --note "The timeout is set by the HTTP client defaults; check its release notes." \
  --now 2026-08-01T09:00:00Z
```

Run on 2026-11-20, more than ninety days after that mark, `status` reports the
claim expired although nothing changed:

```text output
$ hibi status
4 claims: 2 fresh, 0 stale, 1 expired, 1 retired

c1-zfv9r5t784m0vnty4fv9  expired  Each attempt times out after 10 seconds.
  marked 2026-08-01T09:00:00Z (m1-w0yyhnc63nzdvsk0kjb9), recheck P90D ran out at 2026-10-30T09:00:00Z
  next: hibi mark c1-zfv9r5t784m0vnty4fv9

Re-check each statement before running its next command. If it no longer holds, fix the text or the code, or retire the claim with hibi retire.
```

## The current time

"Now" is the wall clock in UTC. `--now <timestamp>`, accepted by every
command, replaces it for reproducible runs: RFC 3339 with any offset, a
fraction of a second dropped. The example above used `--now` to record a mark
in the past; `hibi status --now 2026-10-01T00:00:00Z` reports the same claim
fresh.

## Filtering `status`

| Invocation | Lists |
|---|---|
| `hibi status` | Stale and expired claims |
| `hibi status --state fresh --state retired` | Claims in the given states |
| `hibi status c1-dbv5 c1-24t0` | Exactly these claims, in any state |
| `hibi status --loc 'file:src/**'` | Claims with a side whose locator matches the glob |
| `hibi status --since main` | Stale claims that the changes since `main` caused; see [ranges](/ranges) |

The summary line always counts every claim in the store, before any filter.
