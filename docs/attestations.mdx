An **attestation** records that an actor stood behind a claim at a time, and on what basis. Each claim has an append-only `attestations[]`. Hibi never edits or removes an entry.

```json
{ "by": "human:alice@example.com", "at": "2026-10-22T09:12:00Z", "basis": "vouch", "note": "checked Stripe, still $29" }
```

| field | meaning |
|---|---|
| `by` | the actor |
| `at` | when, as an ISO 8601 instant |
| `basis` | `vouch`, `evidence`, or `ack` |
| `note` | free text; required on an `ack` |
| `evidenceHash` | on an `evidence` attestation: the sha256 of the submitted evidence text |
| `ack` | on an `ack` attestation: what it acknowledges |

## Actors

Actors use the OKF form `<type>:<id>`:

| actor | example | use |
|---|---|---|
| `human:<id>` | `human:alice@example.com` | a person |
| `agent:<name>` | `agent:opus` | a coding agent |
| `process:<name>` | `process:nightly-cron` | a script, a CI job, a workflow runner |

An actor is required on `record`, `attest`, and `evidence`; there is no default. On `record --from-file`, each item may carry its own `by`, and `--by` is the default for items without one. On `evidence`, `--by` may be omitted when every item has `by`.

## Bases

| basis | written by | meaning |
|---|---|---|
| `vouch` | `record`, or `attest` without `--ack` | a bare statement that the claim is true |
| `evidence` | `evidence` | the judge returned `supported` for evidence an actor submitted |
| `ack` | `attest --ack review` or `attest --ack conflict:<id>` | the actor acknowledges a `review` finding or a contradiction, with a note |

An `evidence` attestation is written only when the judge's verdict is `supported` (`supports` at or above `judge.threshold`, and the value rule does not fire). A `refuted`, `review`, or `pending` result writes no attestation.

## The counting rule

`ttl` is measured from the newest **counting** attestation. Two kinds count:

- any attestation with basis `evidence`;
- a `vouch` whose actor starts with `human:`.

An `agent:` or `process:` vouch is recorded and does not count. An `ack` never counts. A claim with a `ttl` and no counting attestation is `expired`.

`attest` returns `countsTowardTtl` so the caller sees which rule applied:

```json
{
  "ok": true,
  "action": "attest",
  "schemaVersion": "v4",
  "claimIds": ["clm_418fde0aee55433e"],
  "attestation": { "by": "human:alice@example.com", "at": "2026-10-22T18:16:03.426Z", "basis": "vouch", "note": "checked Stripe" },
  "countsTowardTtl": true,
  "next": "hibi check"
}
```

## ttl durations

`ttl` is an ISO 8601 duration with integer amounts: `P90D`, `P6M`, `P1Y`, `P2W`, `PT12H`. Years and months add calendar units in UTC; when the target month is shorter, the day is clamped to its last day. Weeks, days, hours, minutes, and seconds add a fixed number of seconds.

`ttl` is required on `attested` claims and optional on `code` and `reference` claims. There is no store-wide default.

`hibi list` shows `ttl` and `expiresAt` per claim. `expiresAt` is null when the claim has no `ttl` or no counting attestation.

## Expiry

A claim is `expired` when it has a `ttl` and either the newest counting attestation plus `ttl` is in the past, or it has no counting attestation.

| command | effect of `expired` |
|---|---|
| `hibi check` | warns, with the reason `expired warns in a whole-store check and gates under check --doc` |
| `hibi check --doc <path>` | gates (exit 2), with the reason `expired gates under check --doc` |

The difference is deliberate. A whole-store check in CI should not fail because time passed. A reader who asks "can I trust this document now?" should get no for an expired claim.

An expired claim of any kind appears in the `check` worklist with reason `expired`; a `code` or `reference` claim can carry a `ttl` too. `hibi list --state expired` lists every expired live claim with its `owner`.

## What clears what

| finding | an agent can clear it by | a human can also clear it by |
|---|---|---|
| `expired` on an `attested` claim | submitting evidence the judge finds `supported` | `hibi attest <id> --by human:<id> --note "<what you checked>"` |
| `expired` on a `code` or `reference` claim | nothing; `hibi evidence` accepts only `attested` claims | `hibi attest <id> --by human:<id> --note "<what you checked>"` |
| never checked (`attested` with a `procedure` or `sources`, no evidence yet) | submitting evidence | nothing else; a vouch does not create a judge verdict |
| `judge: refuted` | submitting newer evidence that is `supported` (`attested` claims), or fixing the sentence | the same |
| `judge: review` | `hibi attest <id> --by <actor> --ack review --note "<why>"`, or submitting clearer evidence (`attested` claims) | the same |
| a conflict | `hibi attest <id> --by <actor> --ack conflict:<other-id> --note "<why>"`, or rewriting one sentence | the same |
| `changed`, `orphaned`, `ambiguous`, `moved` | re-verifying, then `hibi reanchor <id>` | the same |

An agent cannot reset a ttl by vouching. `hibi attest <id> --by agent:<name>` is recorded and `countsTowardTtl` is `false`.

`--ack` accepts any actor. Only use it when the finding is not a problem, and say why in `--note`. An `ack` on a review is pinned to the cache key of the claim's current `supports` verdict. For a `reference` claim that is the key of the request built from its sentence and referenced span as they read now, so an edit to either needs a new ack. For an `attested` claim it is the newest `supports` cache entry, so newer evidence needs a new ack. `--ack review` is an error when the claim has no current `supports` verdict: run `hibi check` first for a `reference` claim, or submit evidence for an `attested` claim. An `ack` on a conflict is written to both claims and pinned to both sentences; it lapses when either sentence changes. See [Conflicts](/conflicts).
