`hibi check` resolves every claim against the working tree, consults the judge cache, runs the [contradiction pass](/conflicts), and prints one **verdict** per claim. Verdicts are computed at check time and never stored. Only judge answers are cached.

```sh
hibi check                      # every claim
hibi check --doc CLAUDE.md      # the claims on one document; expired gates here
hibi check --since origin/main  # the claims touching a file changed since the ref
```

`check` writes nothing except new judge cache entries in `.claims/judge/`. Paths given to `--doc` are normalized to POSIX paths relative to the anchor root, so `./CLAUDE.md` and `CLAUDE.md` name the same document, and the JSON echoes the normalized form. `check --doc` on a path with no registered claims exits 1 with `no claims are registered for <path>; run hibi audit --doc <path>`. Retired claims do not count, so a document whose claims are all retired gets the same error.

## Axes

| axis | values | present |
|---|---|---|
| `doc` | `unchanged`, `moved`, `changed`, `ambiguous`, `orphaned`; `retired` for a retired claim | always |
| `evidence` | the same five, plus `unavailable`; `retired` for a retired claim | when the claim has evidence sides; the worst state over them |
| `judge` | `supported`, `refuted`, `review`, `pending` | when a judgment applies: `reference` claims, and `attested` claims with judged evidence |
| `expired` | boolean | always; see [Attestations](/attestations) |
| `conflicts` | `[{ claimId, probability, reason }]` | always; empty when there are none |

The anchor states are defined on [Anchors](/anchors). The judge states are defined on [Judge](/judge).

For a `reference` claim, the judge is consulted only when both sides are `unchanged` or `moved`. Otherwise the reasons say `judge: not consulted while the doc side is <state>` or `... the evidence side is <state>`, and `judge` is absent. For an `attested` claim, `judge` comes from the newest cached `supports` verdict for evidence submitted with `hibi evidence`.

`judge: pending` has one of three causes, each with its own label: the judge was unavailable (no key, network down, 401 or 403), the judge answered with something hibi cannot use (`judge error: <message>`), or the referenced span is longer than 32,000 characters (`referenced span is longer than 32,000 characters`). None of them fails the run.

## gates, warns, reasons

Each verdict has two booleans and a list of labels:

| field | meaning |
|---|---|
| `gates` | the verdict fails the check |
| `warns` | the verdict needs attention and does not fail the check; never `true` together with `gates` |
| `reasons` | every reason label: anchor changes (prefixed `doc:` or `evidence:`), judge outcomes (prefixed `judge:`), conflict findings, expiry, worklist membership, and gating rules |

Every rule hibi applies shows up as a label. A label you do not understand is a question for the code, not a hidden rule.

## The gating table

| condition | `check` | `check --doc` |
|---|---|---|
| `changed`, `orphaned`, or `ambiguous` on either side | gate | gate |
| `judge: refuted` (at or above `judge.threshold`, or from the value rule) | gate | gate |
| a conflict at or above `judge.threshold` | gate | gate |
| `expired` | warn | gate |
| `moved`, `review`, `pending`, `unavailable` | warn | warn |
| a conflict in review, or a conflict check pending | warn | warn |
| `suggested` or `retired` claim | never | never |

A `suggested` claim that would gate or warn gets the label `suggested claim: never gates or warns`. A `retired` claim is not resolved: its verdict reads `doc: "retired"`, `evidence: "retired"` when it has an evidence side, and carries exactly one reason, `retired claim: never gates or warns`.

## Exit codes

| code | meaning |
|---|---|
| `0` | clean, or warnings only |
| `2` | at least one verdict gates; or, under `--fail-on warn`, at least one warns |
| `1` | operational error: no store, an unknown flag, an unknown `--since` ref, an invalid input, `check --doc` on a path with no registered claims |

Gating means a `changed`, `orphaned`, or `ambiguous` side, a `refuted` judgment, or a conflict on an enforced claim, and `expired` under `--doc`. A judge failure is never an operational error: it makes the judgment `pending`.

`--fail-on` sets the threshold:

| `--fail-on` | exit 2 when |
|---|---|
| `gating` | a verdict gates (the default) |
| `warn` | a verdict gates or warns |
| `never` | never; the JSON still reports everything |

## Remediation

A verdict that needs action carries `remediation`: a menu, most severe condition first. `recommended` names the action to start with, or is `null` when hibi cannot know which is right. `--no-hints` (or `HIBI_ADVICE=0`) drops the menu.

| condition | actions, in order |
|---|---|
| a side `orphaned` | `reanchor` (runs `hibi reanchor <id> --suggest` to find the span), `retire`, `supersede` |
| both sides `changed` | `reconcile`, `reanchor`, `retire` |
| evidence `changed` | `update-claim` (rewrite the sentence if it is now wrong, then reanchor), `reanchor`, `retire` |
| doc `changed` | `reverify-doc`, `reanchor`, `retire` |
| a side `ambiguous` | `reanchor` with a wider span |
| `judge: refuted` | `fix-evidence`, `fix-claim` (no reanchor) |
| conflicts | `reconcile` (names the other claims), then one `ack` per other claim |
| `expired` | `attest` (a human vouch), `evidence` (`attested` claims only) |
| `judge: review` | `ack`, `evidence` (`attested` claims only) |
| a side `moved` | `reanchor` |

Each action has `id`, `title`, `rationale`, and a `command` when one exists. `pending` and `unavailable` add no actions; the reason label says what is missing.

Every `command` runs as printed once the placeholders in angle brackets are filled in:

| action | command |
|---|---|
| `attest` | `hibi attest <id> --by human:<you> --note "<what you checked>"` |
| `ack` on a review | `hibi attest <id> --by <actor> --ack review --note "<why>"` |
| `ack` on a conflict | `hibi attest <id> --by <actor> --ack conflict:<other-id> --note "<why>"` |
| `evidence` | `echo '[{"claimId":"<id>","evidence":"<text>","source":"<where>","summary":"<one line>"}]' \| hibi evidence --from-file - --by agent:<name>` |

The `evidence` action is offered only for `attested` claims, because `hibi evidence` accepts only those. A `reference` claim is judged from the referenced document.

## The worklist

`check` output includes `worklist[]`: the claims an agent should re-check now. A live claim on an active document is listed when:

| reason | claims |
|---|---|
| `expired` | any claim with a `ttl` that ran out, `code` claims included |
| `review` | a `reference` or `attested` claim whose judge state is `review` and not acknowledged |
| `pending` | a `reference` or `attested` claim whose judge state is `pending` |
| `never-checked` | an `attested` claim with a `procedure` or at least one `sources` entry, and no judged evidence yet |

A claim is listed once, with the first matching reason in the order above. Its verdict also carries a `worklist: …` reason. For an expired `code` or `reference` claim, that reason is `worklist: expired: re-verify, then hibi attest <id> --by human:<name>`, because an agent vouch does not reset its ttl. A pure vouch claim (`attested`, with no `procedure` and no `sources`) is listed when it is expired or when its newest verdict is a `review` that is not acknowledged. `hibi list --state pending` returns the same claims.

Each item:

| field | meaning |
|---|---|
| `claimId`, `sentence`, `kind` | the claim |
| `document` | the claim's document path |
| `procedure` | `{ instructions, steps? }` or `null` |
| `sources` | `[{ id?, resource, title? }]` |
| `owner` | the actor to contact, or `null` |
| `lastEvidence` | `{ summary, source, at, by }` from the newest judged evidence, when there is any |
| `reason` | `expired`, `review`, `pending`, or `never-checked` |

| top-level key | meaning |
|---|---|
| `ref` | the git HEAD, or `WORKTREE` when there is no commit |
| `since`, `changedFiles` | with `--since` only |
| `doc` | with `--doc` only: the document path, normalized |
| `summary` | counts; `retired` claims are in none of `gating`, `warning`, `clean`, and `summary.retired` equals the number of verdicts with `doc: "retired"` |
| `summary.conflictPass` | `{ pairs, requests, pending, scope }`: pairs judged, judge requests answered in this run, pairs still pending, and `store` (every pair) or `doc` (only pairs with a claim in the `--doc` document) |
| `documents[].suspect[]` | per claim that gates or warns, and per unretired claim on a superseded or archived document, its most severe status tag, such as `evidence:changed`, `judge:pending`, `conflict`, `conflict:review`, `conflict:pending`, `expired`, `superseded`; never `unchanged` |

`--explain` adds `detail` to each verdict: `docRegion`, `evidenceRegions[]`, `similarity`, and `changes[]` (`{ path, kind: text | ast | value, detail }`). `hibi schema --name Verdict` prints the schema.

`--doc` and `--since` scope the verdicts. Under `--since` the contradiction pass runs over the whole store. Under `--doc` it judges only the pairs with at least one claim in that document; the other claim of a pair may be on any document, so a `--doc` check still sees a conflict with a claim outside it.

Errors from `check` and `list` are printed as the JSON error envelope `{ "ok": false, "error": "…" }` with exit 1 whenever the output is JSON.

## Output format

Human output on a terminal, JSON when piped. `--format human|compact|json|json-pretty` or `--json` overrides. `--overview` renders a per-document table in human output.
