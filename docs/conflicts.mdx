Two documents can each be internally correct and still disagree: the pricing page says $29, the FAQ says $39. Hibi finds such pairs with a contradiction pass that runs over every live claim on every `check`, `list`, and `audit`.

The pass has three steps. Code picks candidate pairs. The [judge](/judge) answers each new pair once. Code decides the outcome from the cached answer.

## Pairing

The pass considers live claims: not retired, on an `active` document. Two live claims form a pair when either rule holds:

1. **A shared rare token.** Both sentences contain a content token that appears in fewer than `max(3, 0.05 × number of live claims)` claims.
2. **Comparable values and a shared token.** Both sentences contain a value of the same kind and unit (for example both state an amount in USD), and they share any content token.

A content token is a run of letters, lowercased, at least 3 letters long, and not in a fixed list of English stop words. Claims in the same document pair by the same rules. There are no topics and nothing to configure.

| constant | value | in `src/engine/pairing.ts` |
|---|---|---|
| rare share | 5 percent of live claims | `RARE_SHARE` |
| rarity floor | 3 claims, so a token shared by exactly two claims is always rare | `RARE_MIN_CLAIMS` |
| shortest content token | 3 letters | `MIN_TOKEN_LETTERS` |

Value kinds and units come from the extraction table described on [Judge](/judge#what-stays-in-code).

## The judge call

Each pair is sent to the `conflict` judgment once. The request holds both sentences, their document paths, and their context (heading path and paragraph), in claim-id order. The answer is cached under the hash of the model and the request. A pair whose sentences and context have not changed is not asked again. At most 8 pairs are asked at a time.

`check` reports the work in `summary.conflictPass`:

| field | meaning |
|---|---|
| `pairs` | pairs formed over the whole store |
| `requests` | judge calls answered in this run; 0 when every pair came from the cache |
| `pending` | pairs the judge could not answer |

The pass always runs over the whole store. `check --doc` and `check --since` scope only the verdicts, so a claim in scope still shows a conflict with a claim outside it.

## Outcomes

Every pair ends with one outcome and one reason label. `threshold` is `judge.threshold` (default 0.8).

| outcome | rule | example label |
|---|---|---|
| `unrelated` | `same_subject` below 0.3 forced the relation to `unrelated` | `not the same subject (same_subject=0.12)` |
| `conflict` | `same_subject` at or above the threshold, and the two sentences hold different values of the same kind and unit | `numbers differ: 29 vs 39` |
| `conflict` | `contradictory`, with confidence and `same_subject` at or above the threshold and `contradicts` at or above 0.5 | `contradictory (p=0.93, same_subject=0.95)` |
| `review` | `contradictory`, with any of those three below its bar | `review: contradictory, confidence=0.55 below threshold 0.80` |
| `duplicate` | `consistent`, with `same_subject` at or above the threshold | `consistent and same subject (same_subject=0.95)` |
| `clean` | anything else | `unrelated (confidence=0.80, same_subject=0.40)` |
| `acked` | a `conflict` or `review` that an ack on either claim covers | `acknowledged: numbers differ: 29 vs 39` |
| `pending` | the judge was unavailable | `judge unavailable: TYPESAFE_API_KEY is not set; the judge cannot answer.` |

The value comparison runs in code, not in the model. It runs only after the judge says both sentences are about the same subject, so `$29` and `$39` in unrelated sentences are not a conflict.

## How outcomes appear on verdicts

| outcome | on each claim of the pair | effect |
|---|---|---|
| `conflict` | an entry in `conflicts[]`: `{ claimId, probability, reason }` naming the other claim; the reason label `conflicts with <id> (p=… at or above threshold …): …` | gates |
| `review` | the reason label `possible conflict with <id>: review: contradictory, …` | warns |
| `pending` | the reason label `conflict check pending with <id>: judge unavailable` | warns |
| `duplicate` | nothing on the verdict; see below | none |

`probability` is the judge's probability for `contradictory`, or `1` when the values differ. A gating conflict adds a `reconcile` action to the claim's [remediation menu](/verdicts), naming the other claim.

`hibi list --state conflict` lists every live claim with a `conflict` or `review` finding.

## Duplicates

A `duplicate` outcome never gates or warns. It is reported in two places:

- `hibi list --state duplicate` lists live claims that have a duplicate candidate from the pass, or another live claim with the same normalized sentence. Each row carries `duplicates[]` with the other `claimId` and a `why` (the pass's reason label, or `same sentence`).
- `hibi audit` sets `duplicateOf` on a covered row to the claim its claim most likely duplicates (the highest probability; ties go to the smaller claim id).

Decide whether to keep both sentences, merge them, or retire one claim.

## Acknowledging a finding

When the two sentences are both correct (for example they describe different plans), acknowledge the pair:

```sh
hibi attest <claim-id> --by human:alice@example.com \
  --ack conflict:<other-claim-id> --note "the FAQ describes the annual plan"
```

`--note` is required with `--ack`. The same `ack` attestation is written to both claims:

```json
{
  "by": "human:alice@example.com",
  "at": "2026-10-22T09:12:00Z",
  "basis": "ack",
  "note": "the FAQ describes the annual plan",
  "ack": { "pairId": "clm_a…:clm_b…", "sentenceHashes": ["…", "…"] }
}
```

The ack is pinned to the hash of each normalized sentence. While both sentences read the same, the pair's outcome is `acked` and it neither gates nor warns. When either sentence changes, the ack no longer matches and the pair is judged again. An ack never resets a ttl. Any actor may ack; see [Attestations](/attestations).
