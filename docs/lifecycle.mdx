Hibi asks two separate questions. May this claim gate? Where is this document in its life? Each has its own field and its own verbs.

## Enforcement

Enforcement is a field on the claim.

| enforcement | meaning |
|---|---|
| `enforced` | The default. The claim may gate (exit 2) and warn. |
| `suggested` | Advisory. Recorded with `record --suggest` (or `"suggest": true` in a `--from-file` item). It never gates and never warns. |
| `retired` | Withdrawn with `hibi retire`. Kept in the store for history. It never gates or warns, the contradiction pass skips it, and `evidence` and `attest` refuse it. |

### `retire`

```sh
hibi retire <claim-id> [--dry-run]
```

Sets the claim's `enforcement` to `retired` and saves it. The claim file stays in `.claims/claims/`; do not delete it by hand. A second call changes nothing and reports `alreadyRetired: true`.

```json
{ "ok": true, "action": "retire", "schemaVersion": "v4",
  "id": "clm_…", "alreadyRetired": false, "next": "hibi check" }
```

In `check`, a retired claim is counted in `summary.retired` and in none of `gating`, `warning`, or `clean`.

## Document lifecycle

Lifecycle is a field on the document record in `.claims/documents/`.

| lifecycle | meaning |
|---|---|
| `active` | In the read path. The default. |
| `superseded` | Replaced by another document. The old document's record carries `supersededBy` with the new document's id. |
| `archived` | Moved to `archive/`, with a tombstone at the old path. |

A live claim (not retired) on a `superseded` or `archived` document is **stranded**. List them with:

```sh
hibi list --state stranded
```

A stranded claim still resolves, still gates, and still warns. In `check` JSON, every live claim on a non-active document appears in that document's `suspect[]` with the lifecycle as its status when nothing worse applies. Claims on a non-active document are left out of the worklist, so no agent is asked to collect evidence for them.

### `supersede`

```sh
hibi supersede --from <old> --to <new> [--dry-run]
```

In one pass:

1. Registers both documents in the store if needed.
2. For every live claim on `--from`, reads the claim's current sentence. If that sentence appears verbatim in `--to`, the claim is reanchored there. It keeps its id, evidence spans, sources, procedure, and attestations; only its document changes.
3. Sets `--from` to `superseded` and records `supersededBy` on it.

```json
{ "ok": true, "action": "supersede", "schemaVersion": "v4",
  "from": "design-v1.md", "to": "design-v2.md",
  "relocated": [{ "claimId": "clm_…", "doc": "design-v2.md", "evidence": "src/retry.ts" }],
  "misses": [{ "claimId": "clm_…", "reason": "documented sentence not found in design-v2.md; reanchor with an explicit span or retire" }],
  "strandedClaims": ["clm_…"],
  "dryRun": false,
  "next": "reanchor or retire each missed claim, then hibi check" }
```

`strandedClaims` lists the live claims still on the old document after the pass. For each miss, move the claim by hand with `hibi reanchor <id> --doc <new> --doc-quote "…"`, or withdraw it with `hibi retire <id>`. When `strandedClaims` is empty, the old file can be deleted or archived without leaving claims behind.

### `archive`

```sh
hibi archive --doc <path> [--successor <path>] [--dry-run]
```

Copies the file to `archive/<path>`, replaces the original with a short tombstone, and sets the document's lifecycle to `archived`. The tombstone is a Markdown page headed `# Archived` that names the old path and, with `--successor`, links to the successor. Claims are not moved.

```json
{ "ok": true, "action": "archive", "schemaVersion": "v4",
  "doc": "old.md", "archivedTo": "archive/old.md", "successor": "new.md",
  "lifecycle": "archived", "strandedClaims": ["clm_…"], "dryRun": false,
  "next": "reanchor or retire each stranded claim, then hibi check" }
```

`archivedTo` is null when the file was not on disk. To withdraw a document that has no successor, archive it without `--successor`.

## Reanchoring a claim

```sh
hibi reanchor <claim-id> [--doc <path>] [--doc-quote <text> | --doc-range L1:L3]
                         [--code-file <path> (--code-quote <text> | --code-range L1:L9)]
                         [--suggest] [--dry-run]
```

`reanchor` re-resolves every span of the claim against the working tree and stores the result as the new baseline, so a `moved` or `changed` side returns to `unchanged`. It also refreshes the claim's `sentence` from the doc span.

- Without span flags, each side is located through its stored selectors.
- A side that resolves `orphaned` is refused unless you pass a new span for it. Hibi does not guess where a lost span went.
- `--doc <path>` with `--doc-quote` or `--doc-range` moves the claim to another document.
- `--suggest` is read-only. It ranks candidate locations for the stored doc and evidence quotes. It cannot be combined with span flags or `--dry-run`.
- `--dry-run` computes the result and writes nothing.

Reanchor only after you have re-read the sentence against its evidence. A reanchor tells hibi that the current text is correct.

## Deleting or renaming a document

Claims belong to the document they quote. Move them in the same change as the prose:

1. `hibi list --path <old-doc>` lists the claims that name the file on either side.
2. `hibi supersede --from <old-doc> --to <new-doc>`.
3. Resolve each entry in `misses` with `reanchor` or `retire`.
4. When `strandedClaims` is empty, delete or archive the old file.

If you skip steps 2 and 3, the claims become `doc: orphaned` after the delete, and an orphaned enforced claim gates. Orphaned is not retired: it is a live record that points at a missing file.

## Who does what

Hibi records lifecycle and enforcement and reports what is stranded or orphaned. A person or an agent rewrites the prose, decides what to reanchor and what to retire, and runs `hibi check` again. Hibi never edits prose; `archive` is the only verb that writes a document, and it writes only the tombstone.
