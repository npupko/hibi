---
title: "Agent workflow"
description: "How an agent uses hibi in a working session: status, re-check, mark or reanchor, claim, cover."
---

hibi is built for an agent that is trusted to judge whether a statement is
true. hibi supplies the memory: which statements were checked, against what,
and what changed since. The agent supplies the judgement, and asks the user
when it cannot decide.

## The session loop

<Steps>
  <Step title="Start with status">
    ```bash
    hibi status
    ```

    By default `status` lists the stale and expired claims, and the fresh
    claims whose anchor drifted (a side was found only approximately). For
    each one it lists the sides that are not the same as at the mark, with a
    state and a reason, and a `next` command. Add `--detail` to include the current text
    of every side, so the re-check needs no extra file reads:

    ```bash
    hibi status --detail
    ```
  </Step>
  <Step title="Re-check each stale or expired claim">
    Read the statement and the current text of its sides. Decide whether the
    statement still holds. `next` is what to run when it does; it is not a
    verdict. hibi prints the reminder once per run: "Re-check each stale or
    expired statement before running its next command. If it no longer holds,
    fix the text or the code, or retire the claim with hibi retire."
  </Step>
  <Step title="Refresh each drifted claim">
    A drifted claim is fresh: every side still has a fingerprint that a mark
    recorded, so the statement still holds as checked. Only the anchor no
    longer matches exactly, for example because the sentence around a quote
    was reworded or an enclosing struct was renamed. Look at the unit the side
    resolves to now. If it is the unit the claim is about, run `next`
    (`hibi reanchor <id>`), which stores a selector that matches exactly
    again. If it is the wrong unit, point the side at the right one with
    `--subject` or `--evidence <n>=<anchor>`.
  </Step>
  <Step title="Record what you found">
    | Finding | Command |
    |---|---|
    | The statement still holds | `hibi mark <id>` |
    | It holds, but a side moved, was reworded or matches several units | `hibi reanchor <id>`, with `--subject` or `--evidence <n>=<anchor>` for the side that moved |
    | The statement must change (you fixed the text, or the code changed what is true) | Fix the text, then `hibi reanchor <id> --statement "..." --subject ...` |
    | The statement was removed or no longer applies | `hibi retire <id> --note "why"` |
    | You cannot tell which side is right, the document or the code | Ask the user. Do not mark. |
  </Step>
  <Step title="Claim what you checked">
    When you write or verify a statement during the session, record it with
    `hibi claim` right after the check, while the evidence is in front of
    you.
  </Step>
  <Step title="Look for gaps">
    ```bash
    hibi cover --since main
    ```

    lists the units of the declared scopes that the branch added or changed
    and that no claim covers. Claim the checkable ones. A unit that states
    nothing checkable can be excluded in `.hibi/hibi.toml` with a reason;
    exclusions are visible in every `cover` report, so agree on them with the
    user.
  </Step>
  <Step title="Before you finish">
    ```bash
    hibi status --since main
    ```

    lists the claims that the branch made stale. Resolve them, then commit
    `.hibi/` with the change.
  </Step>
</Steps>

## Reading `next`

`next` is one command line quoted for a POSIX shell, or `null`. A part you
must supply is written `<anchor>` or `<text>`. hibi picks the first row that
applies:

| Condition | `next` |
|---|---|
| Fresh with no approximate side, or retired | `null` |
| A side is missing or ambiguous | `hibi reanchor <id> --subject <anchor>` or `--evidence <n>=<anchor>`, one option per such side |
| A side is unavailable because its scheme is not declared, its provider is not registered or failed, or a sibling repository is not allowed | `hibi providers` |
| A side is unavailable because a sibling repository was not found, the file is not text or too large, or the provider answered with an error | `null` |
| Fresh, and a side was found only approximately | `hibi reanchor <id>`, or `hibi reanchor <id> --note <text>` when the plain command would recreate a retired claim |
| Otherwise: expired, a side changed, or a side is unavailable with `profile_mismatch` | `hibi mark <id>` |

A stale claim with an approximately found side gets `hibi mark <id>`. After
the mark, the claim is fresh and drifted, and its `next` becomes
`hibi reanchor <id>`. Here the sentence was reworded from "doubles each time"
to "doubles every time"; the meaning is unchanged, so the claim is marked:

```text output
$ hibi mark c1-rj6k --by agent:claude
c1-rj6kbh7y1yw79ywz4msv  marked  m1-3wsdvcvh1ykhahdzx1c3
  was stale: subject file:docs/retry.md changed (fingerprint_differs); evidence 1 file:src/retry.rs changed (fingerprint_differs); now marked
  subject  file:docs/retry.md  same, found approximately  sentence "The delay between attempts doubles every time, starting at …", line 5
    | The delay between attempts doubles every time, starting at 200 ms.
  next: hibi reanchor c1-rj6kbh7y1yw79ywz4msv

A next command here only brings a stored anchor up to date. Look at what the anchor points to now, then run it.
```

`mark` prints the text of every approximately found side, so you see exactly
what you marked. The next `status` lists the claim as drifted, with a second
reminder for it:

```text output
$ hibi status
4 claims: 2 fresh (1 drifted), 0 stale, 1 expired, 1 retired

c1-rj6kbh7y1yw79ywz4msv  fresh  The delay doubles each time, starting at 200 ms.
  marked 2026-11-20T23:57:00Z (m1-3wsdvcvh1ykhahdzx1c3)
  subject  file:docs/retry.md  same, found approximately  sentence "The delay between attempts doubles every time, starting at …", line 5
  next: hibi reanchor c1-rj6kbh7y1yw79ywz4msv

c1-zfv9r5t784m0vnty4fv9  expired  Each attempt times out after 10 seconds.
  marked 2026-08-01T09:00:00Z (m1-w0yyhnc63nzdvsk0kjb9), recheck P90D ran out at 2026-10-30T09:00:00Z
  next: hibi mark c1-zfv9r5t784m0vnty4fv9

Re-check each stale or expired statement before running its next command. If it no longer holds, fix the text or the code, or retire the claim with hibi retire.

A fresh claim is listed because its anchor drifted. The statement still holds: look at what the anchor points to now, then run its reanchor command.
```

`hibi reanchor c1-rj6k` then replaces the claim with one whose anchor matches
exactly, and it is no longer listed.

## JSON for agents

In an agent's shell tool standard output is not a terminal, so each command
prints one JSON object. The fields an agent reads from `status`:

| Field | Meaning |
|---|---|
| `summary` | Counts of every claim in the store by state, before any filter. `drifted` counts the fresh claims with an approximately found side and is part of `fresh`. |
| `claims[].state` | `fresh`, `stale`, `expired` or `retired` |
| `claims[].sides[]` | One entry per side: `index` (0 for the subject, n for evidence n), `role`, `anchor`, `state`, `reason`, `approx`, `unit`, `fp` and `markedFp`, plus `candidates` when ambiguous and `text` with `--detail` |
| `claims[].next` | The command to run after a successful re-check, or `null` |
| `nextNote` | The reminders: re-check a statement before running its `next`; when it no longer holds, fix the text or the code, or retire the claim; and for a drifted fresh claim, look at what the anchor points to now before running its `reanchor` |

Every write that adds a mark to an existing claim (`claim` on an existing
claim, `mark`, `reanchor`) reports what it accepted:
`"accepted": {"was": <state before>, "sides": [{"index", "role", "loc", "state", "reason"}]}`,
listing the sides that were not `same`; for a new claim `accepted` is `null`.
In text this is a line such as
`was stale: evidence 1 file:src/cache.rs changed (fingerprint_differs); now marked`.
Every result that carries a `next` also carries `nextNote`.

Errors are `{"ok": false, "errors": [{"code", "message", "remediation"}]}` with
exit status 1. `remediation` is one sentence or one command that fixes the
cause.

## Batches

`claim` and `mark` read a JSON array from standard input with `--stdin`. A
batch is written all or nothing: if any element fails, nothing is written and
every failing element is reported in the same run, each with its `index`:

```text output
$ echo '[{"statement":"a","subject":"file:docs/nope.md"},{"statement":"b","subject":"file:docs/cache.md::The cache"},{"statement":"c","subject":"file:docs/cache.md::holds 64 entries","recheck":"P0D"}]' | hibi claim --stdin
error: element 0: side_missing: the subject (file:docs/nope.md) resolves to no unit (resource_not_found): not_found: file:docs/nope.md: no such file
  fix: Point the anchor at text that exists in the resource.
error: element 1: side_ambiguous: the subject (file:docs/cache.md): the anchor matches 2 units; use one of these anchors: sentence "The cache holds 64 entries.", line 3: {"loc":"file:docs/cache.md","sel":{"quote":"The cache holds 64 entries.","prefix":"# Cache\n\n","suffix":"\nOld entries are evicted first.\nThe cache is cle","pos":9}}; sentence "The cache is cleared on restart.", line 5: {"loc":"file:docs/cache.md","sel":{"quote":"The cache is cleared on restart.","prefix":"olds 64 entries.\nOld entries are evicted first.\n","suffix":"\n","pos":68}}
  fix: Give a symbol, or a longer quote, so that the anchor matches one unit.
error: element 2: invalid_duration: the recheck period "P0D" is zero; it must be longer than zero
  fix: Give a period longer than zero, for example P90D, or leave the recheck period out.
```

```bash
echo '["c1-zfv9", {"claim": "c1-r0gt", "note": "checked against delay_ms"}]' | hibi mark --stdin
```

```bash
hibi claim --stdin <<'EOF'
[{"statement": "The client retries a failed download.",
  "subject": "file:docs/retry.md::retries a failed download",
  "evidence": ["file:src/retry.rs#MAX_ATTEMPTS"],
  "by": "agent:claude"}]
EOF
```

Each element of a `cover` item list carries an `anchor` object that can be
used as `subject` as it is. `hibi schema claim-input` and
`hibi schema mark-input` print the schemas of these documents.

## Who checked

`--by` (or the `by` field, or the `HIBI_BY` environment variable) is free text
stored with a mark for the record, for example `agent:claude`. hibi never
interprets it.
